# Архитектурные решения

## Область применения

Multi-tenant SaaS с подпиской (не личный инструмент одного человека). Это определяет: `user_id` на каждой таблице с первого дня, JWT-аутентификация, subscription gate перед дорогими (LLM) действиями.

## Каналы

- **Бот — обязательный, основной канал MVP.** Только бот умеет: писать первым (проактивность — ядро ценности продукта) и принимать голосовые сообщения нативно. Mini App/веб не может ни то, ни другое.
- **Веб-кабинет** — не в первой итерации. Появится, когда возникнет первая структурированная сущность, неудобная в чате (вероятно — список задач/фокус-сессий). Строить как обычный веб-апп, детектящий Telegram WebApp SDK (переиспользуется и как отдельный сайт, и как Mini App) — не писать Mini-App-специфичный код.
- Оплата подписки — скорее всего внешний чекаут (ЮKassa/CloudPayments), не через Telegram Payments — Telegram сильно ограничивает приём платежей вне своей экосистемы.

## Слои

```
channels/        адаптеры входа (bot, позже web) — только перевод в/из формата канала
orchestrator/     agent loop: LLM решает, какой tool вызвать, через function-calling
core/             детерминированная бизнес-логика (CRUD, правила) — юнит-тестируема без LLM
llm/              провайдер-абстракция — заменить модель = написать новый класс здесь
integrations/     адаптеры внешних сервисов (Google, GitHub, ...) — единый контракт, ещё не начаты
scheduler/        источник проактивности: опрашивает scheduled_jobs, дергает push через channels
database/         models, alembic migrations
```

Ключевое разделение: **core-модули не знают про LLM**, **orchestrator не знает бизнес-правил** — он только маршрутизирует вызовы инструментов. Это та же причина, по которой n8n (если будет использоваться) должен быть просто ещё одним инструментом за Tool Manager, а не местом, где живут решения ассистента — иначе логика расползается по двум средам и перестаёт быть тестируемой.

## Память (Memory)

**Этап 1 реализован** (миграция `0003_memory`): `conversation_messages` (только финальные user/assistant реплики, не промежуточные tool-call шаги оркестратора) и `user_facts` (короткие факты key/value, сохраняются явно через LLM-инструмент `remember_fact`, не автоизвлечением). `handle_message` (`app/orchestrator/agent.py`) на каждый запрос подтягивает последние `HISTORY_WINDOW` (20) сообщений из БД и известные факты, кладёт их в промпт, а после ответа сохраняет новую пару реплик. Когда сохранённых сообщений становится больше `SUMMARIZE_THRESHOLD` (30), самые старые (всё, что выходит за `HISTORY_WINDOW`) сворачиваются одним LLM-вызовом в `users.memory_summary` (rolling summary) и удаляются — так объём промпта не растёт бесконечно. Проверено вживую: факт, сохранённый в одном сообщении, корректно вспоминается в следующем без доступа к истории переписки внутри одного запроса.

**Этап 2 разблокирован (2026-07-16)** — pgvector теперь доступен (см. «Инфраструктура: Docker + pgvector» ниже), но структурированный семантический поиск по Memory (в отличие от Knowledge Base, где он уже реализован) пока не написан: `user_facts` остаются key/value без эмбеддингов, точный lookup достаточен на текущем масштабе.

## Knowledge Base

**v1 реализован** (миграция `0004_knowledge_base`), scope сознательно ограничен текстовыми заметками — без загрузки файлов/PDF/OCR (это отдельный шаг позже). `documents` (заголовок) + `document_chunks` (текст разбит по ~500 символов с перехлёстом 50, `chunk_index`, `embedding vector(768)`, `user_id` денормализован для запросов без join). LLM-инструменты: `save_note(title, content)` сохраняет и чанкует, `search_knowledge(query)` ищет по косинусной близости (`pgvector` HNSW-индекс, `vector_cosine_ops`) среди чанков пользователя и отдаёт топ-5 как текстовый контекст модели.

**Эмбеддинги — локальная модель, не API**: `sentence-transformers/paraphrase-multilingual-mpnet-base-v2` (768 измерений), обёрнута в свою провайдер-абстракцию `app/embeddings/` (по образцу `app/llm/`) — заменить модель/провайдера означает написать новый класс, реализующий `EmbeddingProvider`. Причина не использовать API: OpenRouter (через который идёт LLM) **не поддерживает embeddings endpoint** — только chat completions; прямой OpenAI недоступен из России (см. ниже); альтернативные облачные провайдеры эмбеддингов потребовали бы отдельной регистрации/ключей. Локальная модель работает офлайн, без ограничений по доступности из РФ, ценой ~1ГБ зависимостей (`torch`, `transformers`) и нескольких секунд CPU-инференса на батч — приемлемо для MVP-масштаба. Модель загружается один раз при старте `app/worker.py` (`get_embedding_provider()`), не лениво на первом сообщении, чтобы не блокировать первый запрос пользователя.

## Инфраструктура: Docker + pgvector (2026-07-16)

Docker Desktop установлен для доступа к pgvector (нативная установка PostgreSQL 17 на этой машине не может собрать/установить расширение без ручной компиляции под Windows — решили не делать этого). Потребовалось включить WSL2-компонент Windows и перезагрузить машину. Локальная БД разработки полностью переехала на `docker-compose` (`pgvector/pgvector:pg16`), нативный PostgreSQL 17 (порт 5432) для этого проекта больше не используется.

Порт Postgres в `docker-compose.yml` — **5434**, не 5433 как было исходно: 5433 на этой машине уже занят посторонним нативным процессом `postgres` (не относится ни к этому проекту, ни к другой проект, источник не выяснялся — Windows-службы с таким именем не зарегистрировано). `.env` → `DATABASE_URL` указывает на `localhost:5434`.

## CRM

**v1 реализован** (миграция `0005_crm`): `contacts` (name, phone, email, company, notes) + `contact_interactions` (свободный текстовый лог, `contact_id` + денормализованный `user_id`). LLM-инструменты: `create_contact`, `log_interaction` (сам находит контакт по точному совпадению имени без учёта регистра или создаёт нового — не блокирует пользователя необходимостью сначала явно завести контакт), `get_contact_info` (карточка + последние 10 записей истории). Поиск контактов — точный lookup по имени, не семантический: для свободного смыслового поиска уже есть Knowledge Base, дублировать pgvector-инфраструктуру здесь избыточно на этом масштабе.

## Habit Analyzer

**v1 реализован**, без новых таблиц — работает поверх уже существующих `focus_sessions`. Scope сознательно уже, чем в vision-документе (сон, настроение, тренировки, соцсети): единственный реально собираемый источник данных сейчас — это фокус-сессии (завершения/срывы, `interruption_reason`, `outcome_note`), остальное не отслеживается нигде и не в этом модуле (тренировки — вообще отдельный проект «Подход»).

`app/core/habits/service.py` только агрегирует (`get_focus_stats`: доля завершения, список причин срывов, список заметок о результатах) — не ищет закономерности сам, это осознанно оставлено модели, тот же принцип «core не знает про LLM», что и везде. LLM-инструмент `get_habit_insights` отдаёт агрегаты как контекст на запрос пользователя; модель формулирует наблюдение своими словами (как в примере из vision-документа — «последние пять раз тебе становилось легче после первых 20 минут», это LLM-инсайт над данными, не предвычисленная метрика).

Проактивная часть — `weekly_habit_summary`, новый `job_type` в `scheduled_jobs` (recurrence `weekly`, поддержано в `app/scheduler/runner.py`), сеется при регистрации так же, как `morning_checkin` (ближайшее воскресенье 18:00 по локальному времени пользователя, тот же UTC-дрифт на DST, что и у утреннего чек-ина). Хендлер сам вызывает LLM (не через `handle_message`/tool loop — это не диалог, а one-shot суммаризация) с сырой статистикой и отправляет результат через `send_message`.

## AI Coach

**v1 реализован без отдельного модуля/таблиц.** Vision-документ описывает Coach как «не мотивирует, а помогает принять решение», и его же пример инсайта («последние пять раз тебе становилось легче после 20 минут») — это ровно то, что уже делает Habit Analyzer. Реальное отличие Coach не в новой аналитике, а в том, *когда* инсайт применяется: в момент решения, а не по явному запросу или раз в неделю. Поэтому v1 — это встраивание `format_coach_hint` (короткая, нерепортажная агрегация: доля завершения + самая частая причина срыва, возвращает `None`, если сессий меньше `MIN_SESSIONS_FOR_COACHING=3` — говорить не о чем) в два существующих момента:

- `_focus_session_hint` в `app/orchestrator/agent.py` — когда сессия предложена, но не начата (`PLANNED`), в системный промпт добавляется факт из истории, который модель может (не обязана — «если уместно») использовать вместо общей мотивационной фразы;
- `_handle_abandon_focus_session` в `app/orchestrator/tools_registry.py` — сразу после того, как пользователь сообщил о срыве, тот же факт подмешивается в результат tool-вызова, чтобы поддержка в ответе была основана на данных, а не была общим утешением.

`SYSTEM_PROMPT` явно проговаривает принцип («не мотивировать общими фразами, а опираться на то, что реально сработало/не сработало у этого пользователя»). Проверено вживую: в сценарии срыва сессии модель корректно вплела реальный процент завершения в поддерживающий ответ; в сценарии старта сессии модель имела доступ к тому же факту, но не сочла нужным его использовать для короткого «погнали» — ожидаемое поведение при мягкой формулировке «если уместно», не баг.

## Planner

**v1 реализован** (миграция `0006_planner`): `projects` (name, description, status) + `project_id` (nullable FK) на `tasks`. Отдельной сущности «цели» нет — по объёму на v1 это то же самое, что проект без гранулярных подзадач, заводить вторую таблицу ради этого избыточно. `create_task` принимает необязательный `project` (имя) и сам находит-или-создаёт проект (`get_or_create_project` в `app/core/planner/service.py`) — тот же паттерн, что `log_interaction` в CRM. Новый инструмент `plan_day` отдаёт список ближайших незавершённых задач (по умолчанию 5, `DAILY_PLAN_LIMIT`).

Логику выбора задачи для утреннего чек-ина (`_pick_top_task` в `scheduler/handlers.py`) **не менял** — она осталась «ближайший дедлайн, иначе последняя созданная»: пока проекты не несут явного приоритета, сортировать по ним нечего. `plan_day` использует ту же сортировку, просто отдаёт несколько задач вместо одной.

API: `GET/POST /projects` (`app/api/routes/projects.py`), `TaskResponse`/`TaskCreateRequest` дополнены `project_id` — задел под будущий веб-кабинет.

## Tool Manager + Google Calendar/Drive/Gmail

**Первая внешняя интеграция реализована** (миграция `0007`). Vision-документ описывает Tool Manager как «единую точку для всех интеграций» — по факту это не отдельный движок, а тот же паттерн, что уже был в `tools_registry.py` (LLM function-calling → handler), только handler дёргает внешний API вместо локальной БД. Новых абстракций поверх этого паттерна не вводили.

**Слои:**
- `app/integrations/google_calendar.py` — чистый HTTP-адаптер (обмен/обновление OAuth-токена, create/list событий), без доступа к БД. Собран на `httpx` (уже была зависимость), а не на `google-api-python-client`/`google-auth-oauthlib` — для десятка REST-вызовов тяжёлый официальный SDK избыточен.
- `app/core/integrations/service.py` — знает про БД: хранение/апдейт credentials, проактивное обновление access token за 5 минут до истечения (`TOKEN_REFRESH_BUFFER_MINUTES`), делегирует сами HTTP-вызовы адаптеру.
- `app/api/routes/integrations.py` — единственный новый веб-роут, `GET /integrations/google/callback`, **без JWT-аутентификации**: это редирект от Google, не наш API-клиент, поэтому пользователь идентифицируется через `state`, а не через токен.

**OAuth-хендшейк бот→веб** — `oauth_connect_tokens`: короткоживущий (10 минут, `CONNECT_TOKEN_TTL_MINUTES`) одноразовый токен. Его `id` используется и как идентификатор пользователя для callback (иначе стейтлесс web-роут не узнает, кто подключается), и как anti-CSRF `state` в OAuth-запросе — одно и то же значение закрывает обе задачи. Бот отправляет пользователю прямую ссылку на `accounts.google.com` (не на наш `/connect`-роут — это не нужно, ссылку можно построить сразу).

**Токены шифруются at rest** (`app/integrations/crypto.py`, Fernet, ключ `OAUTH_TOKEN_ENCRYPTION_KEY` в `.env`) — единственные секреты в проекте, принадлежащие пользователю, а не приложению (в отличие от bot token/API-ключей, которые лежат в `.env` открытым текстом, т.к. это секреты самого приложения).

**Блокер, пройденный пользователем вручную:** Google Cloud OAuth-клиент (client_id/secret) создаётся в консоли Google под аккаунтом пользователя — это не то, что можно сделать программно или от имени пользователя. Локально протестировано без деплоя — Google разрешает `http://localhost` как redirect URI для приложений в статусе Testing.

**Google Drive** добавлен тем же паттерном: OAuth-механика вынесена в общий `app/integrations/google_oauth.py` (Calendar и Drive — один и тот же Google-логин, один и тот же `IntegrationCredential`, просто расширенный список `SCOPES`), `app/integrations/google_drive.py` — адаптер поиска/скачивания файлов. **v1-scope: только Google Docs и обычный текст** (`SUPPORTED_MIME_TYPES` в `google_drive.py`) — PDF/таблицы/изображения не парсятся, то же ограничение, что и у Knowledge Base для вручную сохранённых заметок. `import_drive_document` — не отдельная сущность, а мостик в уже существующий `knowledge_service.save_document`: находит файл по имени (или просит уточнить при нескольких совпадениях), скачивает текст, чанкует и эмбеддит как обычную заметку. Расширение scope у уже подключённых пользователей **требует повторного OAuth-согласия** — Google не выдаёт заново разрешённые ранее данные без явного запроса на объединённый набор scope.

**Известное ограничение:** `oauth_connect_tokens` не чистится (нет TTL-очистки истёкших/использованных строк) — на объёме MVP не проблема, но если понадобится — тривиальный cron/scheduled_job.

Scope запрошен минимальный — `calendar.events` (создание/чтение/изменение событий), не полный `calendar` (управление самими календарями) — из vision-документа нужны были только «создание событий, редактирование, напоминания».

Проверено вживую: реальный OAuth-флоу до конца (пользователь прошёл через настоящий Google-логин), создание события через `handle_message` реально появилось в Google Calendar пользователя, обратный поиск по периоду нашёл его через тот же реальный API — не мок.

**Gmail** добавлен тем же паттерном (`app/integrations/gmail.py`) — scope (`gmail.readonly`, `gmail.send`) был заранее добавлен в общий список ещё при подключении Drive, так что для существующих подключённых пользователей повторное согласие не потребовалось. `list_emails` (опционально с поисковым запросом в синтаксисе Gmail) и `send_email`. Отправка — единственное действие среди Google-интеграций, которое **необратимо и видно третьей стороне**: инструмент явно инструктирует модель подтвердить с пользователем точный текст (получатель/тема/письмо) перед вызовом, а не просто интерпретировать пожелание и сразу слать.

Проверено вживую по-настоящему на обоих направлениях: `list_emails` вернул реальные письма из подключённого ящика; `send_email` (с явного разрешения пользователя на этот конкретный тест) отправил письмо самому пользователю, дошло, `id` подтверждён ответом реального Gmail API.

## LLM-провайдер: переезд с OpenRouter на Yandex Cloud AI Studio (2026-07-17/18)

**Причина:** после деплоя на VPS (см. «Продакшен-деплой» ниже) выяснилось, что OpenRouter отдаёт `403 Access denied by security policy` с обоих IP сервера — заголовок `server: cloudflare` и `cf-ray` подтверждают, что это Cloudflare Bot Management, реагирующий на IP хостинг-провайдера как на дата-центр/бота, а не на конкретный аккаунт или код. С локальной машины (домашний IP) всё работало нормально — блок специфичен именно для дата-центровых сетей.

**Проверка альтернатив с самого сервера** (`curl` с обоих IP): Groq — тоже `403` от Cloudflare; DeepSeek (`api.deepseek.com`), Yandex Cloud, Mistral AI, Together.ai — все отдали `401` (требует ключ, не блокирует) или ответили через собственную инфраструктуру, не Cloudflare. `platform.deepseek.com` (страница регистрации, не API) при этом отдельно оказалась недоступна через CloudFront `403` — причём не только с российского IP, но и с инфраструктуры Anthropic, то есть это не гео-блокировка, а отдельная проблема самого сайта регистрации.

**Выбран Yandex Cloud AI Studio** (OpenAI-совместимый режим) — соответствует философии проекта про RU-хостинг данных (152-ФЗ), уже работал по цене/качеству сопоставимо с GPT-4o-mini после проверки. Отличие от прямого OpenAI/OpenRouter: нужен доп. заголовок `x-folder-id` на каждый запрос — `OpenAIProvider` (`app/llm/openai_provider.py`) получил параметр `extra_headers` (generic passthrough, не привязан к Yandex по названию), `app/llm/factory.py` строит заголовки из настройки `YANDEX_FOLDER_ID`, если она задана. Модель указывается полным URI: `gpt://<folder_id>/yandexgpt/latest`.

**Важный урок по методологии тестирования LLM-провайдеров**: первая проверка (реальная накопленная история диалога тестового пользователя + сложный системный промпт, ~2700 токенов) показала, что YandexGPT **перестаёт вызывать инструменты** при таком объёме контекста — просто отвечает текстом-подтверждением без реального вызова. Та же проблема воспроизвелась и на DeepSeek-V4-Pro (через Together.ai, тоже проверяли как альтернативу) на том же контексте — 2/8 успешных попыток. Причина оказалась не в длине контекста и не в самих моделях: тестовый диалог представлял собой **несвязную солянку** из разных smoke-тестов за сессию (Habit Analyzer, Focus Manager, CRM, Calendar, Drive), с дублирующимися и противоречащими друг другу репликами — на **чистом связном диалоге такой же длины (~2000-2800 токенов) обе модели показали 8/8 успешных вызовов**. Вывод: тестировать tool calling на реалистично длинном контексте нужно обязательно, но контекст должен быть связным диалогом, а не механически склеенными фрагментами разных сценариев — иначе можно ошибочно списать модель со счетов.

**Что не менялось:** `LLM_PROVIDER=openai` в `.env` остался как есть — Yandex OpenAI-совместим по протоколу, отдельный provider-класс не понадобился, только опциональный extra-header механизм.

## Продакшен-деплой (2026-07-17/18)

Причина: бот работал только пока включён компьютер разработчика — реальное использование требует постоянно работающего сервера.

**Инфраструктура — переиспользован существующий VPS** (общий VPS, на котором уже живут другие сервисы), не отдельный сервер — сознательный выбор пользователя, несмотря на риск делить ресурсы с чужим кодом. Потребовался апгрейд тарифа (1 vCPU/~1GB RAM → 1.9GB RAM, 14GB диска) — на исходном тарифе после установки зависимостей свободной памяти было ~460MB, торч+эмбеддинги туда физически не влезли бы.

- **PostgreSQL 16 + pgvector — нативная установка** (`apt install postgresql-16 postgresql-16-pgvector`, пакет есть в стандартных репозиториях Ubuntu 24.04), не Docker — экономит память на демоне контейнеризации на и без того стеснённом сервере. Роль/база `ai_assistant`/`ai_assistant_core`, отдельные от баз других проектов на этом сервере.
- **torch — обязательно CPU-only сборка** (`pip install torch --index-url https://download.pytorch.org/whl/cpu`), НЕ через `pip install torch` напрямую — дефолтный PyPI-wheel тянет полный CUDA-стек (гигабайты пакетов nvidia-*), что на сервере без GPU сразу же забивает диск (`No space left on device` при первой попытке).
- **systemd-сервис** `ai-assistant-worker` (`/etc/systemd/system/ai-assistant-worker.service`) — только `app.worker` (бот + планировщик), не `app.main` (FastAPI). Осознанно: `app/channels/telegram_bot/bot.py` не зависит от FastAPI/JWT вообще (сам вызывает `get_or_create_user` по `telegram_id` в хендлере), так что для решения задачи «бот работает без включённого компьютера» веб-часть не нужна.
- **Redis — переиспользован системный `redis-server`** (уже запущен для другого сервиса), новый контейнер/инстанс не поднимался — просто отдельный db-индекс (`redis://localhost:6379/2`) для изоляции.

**Google Calendar/Drive/Gmail сознательно не работают в этом деплое** — `/integrations/google/callback` требует публичный HTTPS-домен (Google OAuth не примет `http://localhost` как redirect URI вне контекста локальной разработки), а домен+nginx+certbot для этого проекта ещё не настроены. `.env` на сервере содержит те же Google-credentials, что и локально, но `GOOGLE_REDIRECT_URI`/`APP_BASE_URL` всё ещё указывают на `localhost:8000` — если реальный пользователь попробует подключить календарь через задеплоенный бот, получит нерабочую ссылку. Осознанно отложено, следующий шаг — поддомен уже существующего домена (например `ai.example.com`).

## Эмоциональная поддержка (не психолог, но может поддержать разговор)

**Продуктовое решение 2026-07-18**: изначально ассистент был жёстко ограничен рамками задач/фокуса и отказывался обсуждать личные переживания. По итогам живого теста пользователем (реальный человек написал боту «поговори со мной как психолог») решено расширить: ассистент **может** поддержать разговор о переживаниях в сочувствующем тоне, но:
- обязан явно проговорить один раз в начале такого разговора, что он не лицензированный психолог и его слова не профессиональная рекомендация;
- при признаках острого кризиса (мысли о причинении себе вреда) **обязан** эскалировать на горячую линию психологической помощи (8-800-2000-122, круглосуточно, вся Россия) вместо попытки самостоятельно «разрешить» ситуацию разговором — это не переговариваемое правило, в системном промпте прописано отдельно от остальных инструкций.

Реализовано целиком в `SYSTEM_PROMPT` (`app/orchestrator/agent.py`), без новых инструментов/таблиц. Проверено вживую: обычный запрос о переживаниях получает дисклеймер и поддержку; сообщение с формулировкой о причинении себе вреда корректно уходит в жёсткую эскалацию на горячую линию, а не в попытку «поговорить об этом».

## Постоянное меню бота (reply keyboard)

**Реализовано** — `app/channels/telegram_bot/keyboards.py`, чисто Telegram-специфичная презентация (живёт в channels-слое, не в core/orchestrator). Шесть кнопок в два столбца: Мои задачи, Добавить задачу, План на день, Фокус-сессия, Подписка, Продуктивность.

Две категории обработки в `bot.py`:
- **Мои задачи / Подписка** — отвечают напрямую, без похода к LLM (`_format_tasks`/`_format_subscription`): это просто вывод данных, гонять его через модель — лишняя задержка и стоимость токенов без пользы.
- **План на день / Фокус-сессия / Продуктивность** — не новая логика, просто отправляют канонiческую текстовую формулировку в уже существующий `handle_message` (`PROMPT_FOR_BUTTON` в `keyboards.py`), которая срабатывает через уже готовые инструменты (`plan_day`, `start_focus_session`, `get_habit_insights`) — кнопка это просто быстрый способ не печатать текст руками.
- **Добавить задачу** — просто просит описать задачу; следующее сообщение пользователя обрабатывается обычным образом (LLM сама поймёт, что это create_task).

## Проверка выполнения задачи после напоминания (follow-up)

**v1 реализован** (миграция `0009`) — тот же DB-state-hint паттерн, что и Focus Manager, применён к обычным задачам. Раньше `_handle_task_reminder` просто слал «⏰ Напоминание: X» и всё, никакого способа отметить задачу выполненной у ассистента не было (`complete_task` не существовал вообще). Теперь: при срабатывании напоминания задача помечается `awaiting_confirmation=True` и вопрос формулируется как чек-ин («X — получилось сделать?»); `_task_followup_hint` (`app/orchestrator/agent.py`) на следующем сообщении подмешивает в системный промпт факт «пользователя только что спросили про задачу N» с её `task_id`, и **сразу сбрасывает флаг** (fire-once, чтобы подсказка не липла к последующим несвязанным сообщениям). Новый инструмент `complete_task` (`task_id` или `title`) помечает задачу выполненной — вызывается моделью либо по этому hint'у, либо когда пользователь сам говорит «сделал X» вне контекста напоминания.

Проверено вживую оба исхода: подтверждение («да, сделал») → `status=done`; отрицание («не успел») → `status` остаётся `pending`, флаг всё равно сброшен.

## Голосовые сообщения (Yandex SpeechKit)

**Реализовано** — `app/integrations/speech_to_text.py`, синхронное распознавание коротких аудио (`POST .../speech/v1/stt:recognize`). Telegram voice-сообщения уже в формате OGG/Opus — это дефолтный формат SpeechKit, конвертация (ffmpeg и т.п.) не нужна вообще, байты идут в API как есть.

**Полезная находка**: тот же API-ключ, что уже используется для LLM (Yandex Cloud AI Studio), подошёл и для SpeechKit без создания отдельного сервисного аккаунта — проверено прямым запросом (тестовый некорректный OGG вернул `400 ogg header has not been found`, а не `401`/`403`, то есть авторизация прошла).

В `bot.py`: голосовое сообщение скачивается через `bot.get_file`/`bot.download_file`, распознанный текст отправляется пользователю отдельным сообщением («🎤 распознанный текст») для прозрачности (чтобы было видно, если STT ошиблась), и дальше уходит в тот же `handle_message`, что и обычный текст — никакой отдельной логики обработки голоса на уровне оркестратора не потребовалось.

## Продакшен: FastAPI + Mini App + публичный домен (2026-07-19/20)

Домен для HTTPS решён без покупки: **nip.io** (бесплатный DNS-сервис — любой поддомен вида `<имя>.<IP>.nip.io` резолвится на этот IP) + `certbot certonly --nginx` для реального Let's Encrypt-сертификата под этим именем. **Важная находка**: основное имя сервера уже было занято другим сайтом на этом же VPS — `nginx -t` предупредил о конфликте имён серверов при попытке добавить второй `server_name` с тем же значением. Ушли на отдельный поддомен `ai.example.com` со своим сертификатом — конфликт устранён, соседний сайт не затронут (перепроверено вживую после отката первой попытки).

Новый systemd-сервис `ai-assistant-api` (`uvicorn app.main:app`, порт 8001, только на `127.0.0.1` — наружу не торчит напрямую) — существует отдельно от `ai-assistant-worker` (бот+планировщик): FastAPI нужен только для Mini App API и OAuth-колбэков, у бота своя независимая зона ответственности. nginx-сайт `ai-assistant` (по образцу уже существующего соседнего nginx-сайта на этом сервере): статика фронтенда (`frontend/dist`, собран через `npm run build` прямо на сервере — Node 20 уже стоит) на `/`, реверс-прокси на 8001 для `/auth`, `/tasks`, `/projects`, `/focus`, `/agent`, `/integrations`, `/health`.

`APP_BASE_URL`/`GOOGLE_REDIRECT_URI` в проде переключены на новый домен — Google Calendar/Drive/Gmail теперь **реально работают в проде**, не только локально (нужно было добавить этот redirect URI в список разрешённых в Google Cloud Console — сделал пользователь, я не могу).

Кнопка Mini App в reply-keyboard (`app/channels/telegram_bot/keyboards.py`) собирается динамически: если `APP_BASE_URL` не начинается на `https://` (как в локальной разработке), кнопка не добавляется вообще — Telegram всё равно откажет на `http://`, лучше не показывать нерабочую кнопку, чем показывать и получать необъяснимую ошибку.

## Баг: зависшие «planned»-фокус-сессии (найден по живому фидбеку 2026-07-20)

**Симптом**: реальный тестер получал каждое утро «У тебя ещё не закрыта вчерашняя фокус-сессия», хотя ни разу её не начинал (`started_at IS NULL`). При попытке закрыть — путаница между фокус-сессией и не связанной задачей, затем «нет активной сессии для завершения».

**Причина**: `planned` (предложенная, но не начатая) сессия входит в `OPEN_STATUSES`, но ни `complete_session`, ни (до фикса) `abandon_session` не умели её трогать — единственный валидный переход был `start_session`. Если пользователь просто игнорировал утреннее предложение, оно оставалось в `planned` **навсегда** и каждое следующее утро подхватывалось как «незакрытая» — хотя по факту это было просто непринятое приглашение, а не реальная незавершённая работа. Найдено на реальных данных прода: две сессии висели с 18-19 июля.

**Фикс**:
- `abandon_session` (`app/core/focus/service.py`) теперь принимает и `planned` — отклонённое/непринятое предложение переходит в `abandoned`, а не застревает.
- `_handle_morning_checkin` (`app/scheduler/handlers.py`) при обнаружении `planned`-сессии **не переиспользует её и не шлёт вводящее в заблуждение «не закрыта»** — молча списывает как `abandoned` («не принято, заменено новым предложением») и предлагает свежую задачу дня, как будто открытой сессии не было вовсе. Сообщение «ещё не закрыта» теперь шлётся только для реально начатых (`active`/`awaiting_followup`) сессий.
- `_focus_session_hint` для `planned`-статуса (`app/orchestrator/agent.py`) теперь явно инструктирует модель вызывать `abandon_focus_session` при явном отказе/просьбе отменить — раньше промпт прямо запрещал вызывать любой инструмент в этом случае, оставляя отказ ни к чему не приводящим.

**Известное смежное ограничение, не устранено полностью**: если одновременно активны и `_focus_session_hint`, и `_task_followup_hint` (оба используют одинаковый грамматический род в русском — «сессия» и «задача» обе женского рода, местоимение «её» грамматически неоднозначно), модель может спутать, к чему относится «закрой её». Понижает вероятность после фикса выше (зависшие sessions больше не копятся), но не устраняет в принципе — при необходимости потребует явного различения тем в промпте или структуры «одна открытая тема за раз» вместо параллельных хинтов.

Проверено вживую: искусственно состаренная (2 дня) `planned`-сессия корректно списалась при следующем утреннем чек-ине, вместо нее предложена свежая; явный отказ от свежепредложенной сессии («отмени, не буду начинать») корректно вызвал `abandon_focus_session` и получил осмысленный ответ.

## Единый формат списка задач

**Найдено и исправлено 2026-07-18**: `bot.py`'s «Мои задачи» и LLM-инструмент `plan_day` имели две отдельные, расходящиеся друг с другом реализации форматирования списка — из-за этого пользователь получал разный вид ответа в зависимости от того, как спросил (кнопкой или текстом), и время `due_at`/`remind_at` показывалось **в UTC, а не в часовом поясе пользователя** (реальный баг, не просто расхождение стиля). Обе точки теперь используют один `format_task_list` (`app/core/tasks/service.py`) — с явной конвертацией через `ZoneInfo(user.timezone)`, отметкой `✅` для выполненных задач и единым форматом времени `(ЧЧ:ММ)`.

Отдельно добавлена инструкция в `SYSTEM_PROMPT`: когда инструмент вернул готовый список, приводить его как есть, не пересказывать абзацем своими словами. Причина — живой баг-репорт: на сильно захламлённой тестовой истории (десятки несвязанных smoke-тестов в одном разговоре) модель на вопрос «во сколько?» отвечала не по свежему результату `plan_day`, а по остаткам памяти о более ранних репликах разговора. На чистом пользователе без такой истории (проверено отдельно) `plan_day` и без этой инструкции работал корректно — но инструкция всё равно оставлена как защита от подобного дрейфа на длинных реальных диалогах.

## Напоминания на точное время (task reminders)

**v1 реализован** (миграция `0008`) — закрывает разрыв, который раньше был явно проговорен в `SYSTEM_PROMPT`: `create_task`/`due_at` не триггерили никакого уведомления. `tasks.remind_at` — отдельное от `due_at` поле (`due_at` — дедлайн, `remind_at` — «разбуди меня в момент X», разные смыслы, у задачи может быть и то и другое, и что-то одно). Если `create_task` вызван с `remind_at`, сразу создаётся одноразовый `scheduled_job` (`job_type=task_reminder`, `recurrence` не задан — планировщик деактивирует его после первого срабатывания, как и было для focus_followup). Хендлер (`_handle_task_reminder` в `scheduler/handlers.py`) при срабатывании проверяет статус задачи — если она уже выполнена/удалена, тихо ничего не шлёт, не будит пользователя ради неактуального пункта.

**Сознательно не сделано в v1**: повторяющиеся напоминания (каждый день/неделю в одно время, кроме уже существующих morning_checkin/weekly_habit_summary) — `SYSTEM_PROMPT` явно инструктирует модель говорить пользователю, что это не поддерживается, а не создавать задачу молча без реального уведомления, как раньше.

**Реальный баг, найденный сразу после первого релиза фичи**: модель не знала текущих даты/времени вообще — для абсолютного времени («в 8:40») она угадывала «сегодня» из контекста разговора более-менее успешно, но для относительного («через 2 минуты») ей не от чего было оттолкнуться, и вместо честного «не знаю текущее время» она сочиняла неправдоподобное оправдание («не могу установить напоминание на такой короткий срок»). Исправлено — `_current_time_context` (`app/orchestrator/agent.py`) добавляет текущие дату/время/день недели в часовом поясе пользователя в системный промпт на каждый запрос, а не только при работе с календарём/фокус-сессиями. Проверено вживую: то же самое «через 2 минуты» после фикса корректно посчиталось от реального текущего времени.

## Проактивность

`scheduled_jobs` — источник истины, не встроенная память APScheduler: своя таблица, timezone-aware `next_run_at`, планировщик — это просто поллер раз в 60 секунд (`app/scheduler/runner.py`). Причина: проактивные триггеры персональные и per-user, и таблица даёт видимость/отладку через обычные SQL-запросы, а не через внутренности APScheduler.

Известное упрощение (пока не проблема, но не забыть): периодичность `daily` считается как +24 часа в UTC, не как "то же самое время в таймзоне пользователя" — сдвигается на переходах DST. Нормально для MVP, пересмотреть, когда джобы начнут планироваться явно из `user.timezone`.

## Focus Manager и диалоговый контекст без Memory

`app/orchestrator/agent.py:handle_message` собирает `messages` с нуля на каждое входящее сообщение — истории переписки нет (Memory ещё не реализована), поэтому LLM не помнит, что сама спросила на предыдущем шаге. Для Focus Manager это критично: сценарий «утром предложили сессию → пользователь согласился → через 90 минут спросили что сделал → пользователь ответил» требует, чтобы модель понимала, на что отвечает пользователь, не видя своих прошлых реплик.

Решение — состояние диалога живёт не в истории сообщений, а в `focus_sessions.status` (`planned` → `active` → `awaiting_followup` → `completed`/`abandoned`). Перед каждым вызовом LLM `handle_message` читает открытую сессию пользователя из БД и, если она есть, добавляет в system-промпт короткую подсказку («у пользователя предложена сессия, если это согласие — вызови `start_focus_session»`, аналогично для follow-up). Модель за один шаг решает, что означает пришедшее сообщение, без доступа к прошлым репликам — потому что весь нужный контекст уже лежит в строке БД, а не в истории чата.

Это осознанный временный паттерн, а не архитектурная замена Memory: он работает, пока у пользователя открыта не больше одной сессии за раз (это гарантируется в `app/core/focus/service.py`). Для будущих модулей с более сложным диалоговым состоянием (Coach, Habit Analyzer) этого может не хватить — тогда нужна будет настоящая история сообщений из Memory-модуля.

**Подмена подтверждения полным списком задач**: голосовая команда «поставь задачу на завтра ... актуализировать задачи по дизайн-студии» создавала задачу корректно, но модель следом сама вызывала `list_tasks`/`plan_day` и, следуя уже существующей инструкции «приводи список дословно», отдавала пользователю дамп всех текущих задач вместо простого подтверждения создания - создание терялось за списком. **Лишний вопрос «всё верно?» перед сохранением**: регрессия без видимой причины в коде (ни один тул не требует подтверждения, `_handle_create_task` сохраняет сразу) - похоже на дрейф самой модели. Добавлена явная директива: если данных достаточно, действовать сразу, подтверждать по факту вызова, не спрашивать разрешения заранее.

**Google Calendar (решение согласовано с пользователем)**: раньше задача и календарь были не связаны вообще - `create_calendar_event` отдельный тул, вызывается моделью только по явной просьбе, без защиты от повторного вызова (дубли «через раз»). Best-effort по дизайну - любая ошибка синхронизации (не подключён, токен истёк, сбой API) логируется и проглатывается, никогда не блокирует саму операцию с задачей. Проверено вживую на реальном пользователе с уже истёкшим Google-токеном - создание задачи прошло успешно, ошибка синхронизации осталась только в логе, как и задумано.

**Просроченные задачи без due-даты никогда не проверялись (объединение двух запросов пользователя)**: пользователь просил и автоматический перенос невыполненных задач на завтра, и чтобы ассистент спрашивал, что случилось - по согласованию с пользователем это объединено в одно: новый ежедневный джоб `evening_review` (21:00 по локали пользователя, seed в `app/auth/service.py` + бэкфилл для уже существующих пользователей в миграции `0015`) находит все просроченные `pending`-задачи (`get_overdue_pending_tasks`), помечает их `awaiting_confirmation` и спрашивает одним сообщением. `get_awaiting_confirmation_task` стал `get_awaiting_confirmation_tasks` (список, не одна задача) - `_task_followup_hint` (`app/orchestrator/agent.py`) теперь умеет и одиночный `task_reminder`-кейс, и пачку от `evening_review`: подтверждённые пользователем задачи завершаются `complete_task`, остальные автоматически переносятся на завтра через `update_task` (без повторного вопроса «переносить?» - см. пункт про лишние подтверждения выше).

**Задача Сергея «затесалась» не на тот день**: в репорте не было исходного текста/голосового, которым ставилась задача - только итоговый список, поэтому нельзя было отличить реальный баг в коде от разовой ошибки модели в конкретной фразе. **«Задачи на сегодня» без деления на актуальные/выполненные**: новые `get_today_overview`/`format_today_overview` (`app/core/tasks/service.py`) показывают два блока; «выполненные сегодня» определяется по `updated_at` (нет отдельного `completed_at` - ничего не трогает `updated_at` у уже `DONE`-задачи после завершения, так что это безопасный прокси).

## Найден и исправлен реальный баг: модель молча меняла дату у не упомянутой задачи (2026-07-27, вечер)

**Симптом**: у Сергея задача «Собрание по меге» (создана на сегодня 19:40) внезапно оказалась перенесена на завтра, хотя он её не трогал.

**Причина, восстановлена по conversation_messages**: два сообщения с разницей в 2 минуты. Первое - «Поставь задачу на сегодня на 19:40 собрание по меге» - создало задачу верно (remind_at = сегодня 19:40). Второе - совершенно не связанный запрос «Напомни мне в среду в 9:00 забрать трафареты...» - должно было только создать НОВУЮ задачу про трафареты, но модель в том же ходу ЗАОДНО вызвала create_task повторно для «Собрание по меге» (не запрошено пользователем вообще), с уже неверно вычисленной датой (завтра вместо сегодня) - и существующий merge-dedup в `create_task` (`_find_recent_duplicate`, окно 2 часа, для защиты от настоящих дублей) молча смёржил это в исходную задачу, перезаписав корректное время. Ответ модели пользователю даже текстуально противоречил тому, что реально попало в БД («...обновлена с напоминанием на сегодня в 19:40», хотя реально записано «завтра»).

Данные Сергея восстановлены вручную (`update_task` напрямую, не raw SQL - чтобы заодно верно обновился и уже созданный Google Calendar event, не только сама задача).

**Фикс** - новая директива в `SYSTEM_PROMPT`: не вызывать create_task/update_task/complete_task для задачи, не упомянутой в ТЕКУЩЕМ сообщении, даже если недавно в разговоре обсуждалась похожая. Проверено вживую (4 прогона того же сценария на throwaway-пользователях, реальная модель) - повторный вызов для несвязанной задачи ни разу не произошёл после фикса.

Отдельно замечено при тестировании (не тот же баг, другой временной контекст): при запросе "на сегодня в HH:MM", если это время уже прошло на момент сообщения, модель иногда трактует это как "на завтра" - разумное, а не ошибочное поведение (бессмысленно ставить будущее напоминание на прошедший момент), не путать с багом выше.

## Многозадачный вечерний обзор: пропуск задачи + путаница направления (2026-07-27, вечер, найдено по фидбеку Сергея)

**Симптом**: Пользователь одним сообщением без знаков препинания перечислил статус 4 задач сразу («Х выполнено Y не выполнено Z не выполнена W выполнена»). Бот обработал 3 из 4 - одна («Проверить названия аттракционов») осталась вообще нетронутой (ни complete_task, ни update_task), не упомянута даже в ответе. Подтверждено по `conversation_messages` и текущему состоянию задачи в БД (due_at всё ещё от 24.07, `awaiting_confirmation` уже сброшен - значит попадёт под замечание только на следующем `evening_review`).

**Фикс, часть 1 - детерминированная проверка полноты**: `_task_followup_hint` теперь возвращает не только текст подсказки, но и список задач, которые были ей затронуты (`app/orchestrator/agent.py`). После основного цикла `handle_message` сверяет состояние каждой из этих задач ДО и ПОСЛЕ хода - если какая-то осталась `pending` с неизменным `due_at`/`remind_at`, значит инструмент для неё не вызывался вообще, и это не полагается на то, заметит ли модель сама свой пропуск. Для найденных пропущенных - один корректирующий вызов с `force_tool_call=True` (тот же механизм, что и для preemptive-confirmation), явно называющий пропущенные задачи по имени и id.

Живой тест (throwaway-пользователи, реальная модель, точное сообщение Сергея) - **пропущенных задач не осталось ни в одном из последующих прогонов** после этого фикса (было: 1 из 4 задач тонет без следа).

**Фикс, часть 2 - осталась частично нерешённой проблема направления**: даже когда пропущенная задача теперь гарантированно обрабатывается, модель иногда путает direction (отмечает как выполненную ту, что пользователь явно назвал невыполненной) при разборе неоднозначного текста без пунктуации. Усилил формулировку подсказки (явно про голосовой ввод без знаков препинания, "статус относится к названию перед ним") - улучшило точность (было ~1/4 полностью верных прогонов, стало ~2/5), но не решило до конца: это упирается в объективную неоднозначность самого текста ("задача1 выполнено задача2 не выполнено" без запятых genuinely трудно разобрать однозначно даже человеку), а не в код. Дальнейшее прompt-инженерное давление показало убывающую отдачу - решил не продолжать бесконечно, только зафиксировал остаточный риск.

**Не сделано**: структурный fallback (спрашивать по одной задаче за раз, если формулировка неоднозначна) - усложнит и замедлит UX, пока не запрошено пользователем явно.

## Поддержка длинных голосовых сообщений (2026-07-27, найдено по фидбоку - 54-секундное сообщение молча падало)

**Причина, подтверждена дословно ответом самого API**: `stt.api.cloud.yandex.net/speech/v1/stt:recognize` (синхронный метод, единственный использовавшийся) жёстко отклоняет аудио длиннее ~30 секунд - `{"error_code":"BAD_REQUEST","error_message":"audio duration should be less than 30s"}`. Раньше любая ошибка на этом эндпоинте просто превращалась в общее "не получилось распознать" без разбора причины.

**Рассмотренный и отклонённый вариант** - долгоиграющее (async) распознавание Yandex SpeechKit (`v2/longRunningRecognize`): подтверждено вживую, что оно **не принимает аудио инлайном** (`content` в base64) - только через `uri`, то есть требует, чтобы файл уже лежал в Yandex Object Storage. Заводить целый новый контур (бакет, сервис-аккаунт, ключи доступа) только ради этого не оправдано.

**Реализовано вместо этого**: `app/integrations/speech_to_text.py` при ошибке короткого метода режет аудио на куски по 25 секунд через `ffmpeg`/`ffprobe` (новая системная зависимость, установлена на сервере через apt) и прогоняет каждый кусок через тот же, уже рабочий, короткий метод, затем склеивает текст по порядку.

**Проверено вживую, не только гипотетически**: сгенерировал сам тестовый звук - сначала синтетический тон через `ffmpeg` (проверить, что механизм разбиения и повторных вызовов не падает), затем **реальную русскую речь ~36 секунд через Yandex TTS** (тот же аккаунт) - весь текст распознался связно и в правильном порядке, включая стык между кусками (там всего один мелкий артефакт ровно на границе среза - ожидаемая цена chunking, не баг).

**Системная зависимость**: `ffmpeg`/`ffprobe` теперь обязательны в окружении `app.worker` (установлены через `apt-get install ffmpeg` на проде) - не отражено в коде как явная проверка при старте, при отсутствии просто тихо не сработает разбиение длинных сообщений (короткие продолжат работать как раньше).

## Ещё один пропуск в детерминированном day-query fast path (2026-07-28, найдено по фидбеку)

**Симптом**: голосовое "Также задача на завтра купить стиральный порошок." (сразу после успешно созданной другой задачи) не создало задачу вообще - бот ответил бare-списком существующих задач на завтра.

**Причина**: fast path в `bot.py` (`_resolve_day_query_date`) перехватывает сообщение, если оно содержит "задач"/"дел" + слово дня и НЕ содержит слова из блок-листа действий (напомни/добавь/поставь/...). Фраза не содержала ни одного из перечисленных глаголов - блок-лист action-verb'ов принципиально не может быть исчерпывающим (бесконечно много способов сформулировать "добавь задачу" без конкретного глагола).

**Фикс - более надёжный сигнал вместо расширения списка глаголов**: единственное число "задача"/"задачу" (именительный/винительный) практически всегда означает описание ОДНОЙ новой задачи, а не запрос списка - настоящие day-query почти всегда используют множественное число ("задачи на завтра", "какие дела", кнопки "Задачи на сегодня/завтра"). Добавлено `\bзадач[ау]\b|\bдел[оу]\b` в exclude-паттерн - это грамматический, не лексический сигнал, поэтому не требует пополнения списком глаголов на каждый новый инцидент.

Проверено: юнит-тестами самой regex-функции (creation-фразы → None, кнопки и настоящие queries → резолвятся как раньше) и живым сквозным тестом через `handle_message` на реальной модели - обе задачи из инцидента создаются корректно, оба ответа явно называют, что добавлено.

**Попутно усилена инструкция в `SYSTEM_PROMPT`**: результат вызова инструмента нельзя подменять отвлечённой фразой без упоминания сути ("Если у вас есть ещё вопросы, сообщите") - у первой задачи из этого же инцидента (`create_task` реально сработал) ответ пользователю не называл, что создано.

Пропущенная задача "Купить стиральный порошок" добавлена пользователю вручную тем же кодом, что использует сам бот (`create_task`), с тем же временем по умолчанию, что и у соседней задачи из того же инцидента.

## Дубликаты задач больше не требуют уточнения - детерминированный фикс (2026-07-28)

**Симптом**: пользователь ответил на уточнение по двум парам задач-дублей обобщённо («закрой их», затем «все») - бот дважды подряд дословно повторил один и тот же уточняющий вопрос, никак не продвигаясь, и только третья, иначе сформулированная фраза («все перечисленные задачи») сработала.

**Первая попытка фикса (промпт-инструкция) не оправдала себя при живом тестировании** - в одном из трёх прогонов модель, наоборот, начала молча выбирать одну задачу из дублей при ПЕРВОМ же обращении, ещё до вопроса пользователя, нарушая соседнее правило "не выбирай сам". Отменил эту правку (see git blame/этот же файл чуть выше) - ещё один случай, когда промпт-директива недостаточно надёжна сама по себе для детерминированного поведения.

**Настоящий фикс - в коде, не в промпте**: `_resolve_pending_task` (`app/core/tasks/service.py`, общая для `complete_task`/`update_task`/`delete_task`) теперь при нескольких найденных по названию совпадениях проверяет, различимы ли они (`_same_slot`: совпадают title+due_at+remind_at). Если все совпадения - буквальные неразличимые дубликаты (последствие уже известного в этом проекте бага задвоения при создании), они обрабатываются ВСЕ сразу, без уточняющего вопроса вообще: спрашивать "какую из двух одинаковых" не даёт пользователю никакой полезной информации для выбора. Если совпадения реально разные (разное время/детали) - поведение не изменилось, по-прежнему возвращается список кандидатов на уточнение.

Живой тест на реальной модели: 4 из 4 прогонов - обе неразличимые копии закрываются одним сообщением без вопроса, несвязанная третья задача не затронута.

**Отдельно найден при тестировании, не пофикшен в этом заходе (не входил в исходный репорт)**: для ДЕЙСТВИТЕЛЬНО неоднозначных совпадений (разные задачи с одинаковым названием, разное время) модель иногда молча выбирает одну вместо того, чтобы спросить, как и предписывает промпт ("не выбирай сам") - воспроизведено вживую отдельным тестом. Это не регрессия от сегодняшнего фикса (старый код вёл бы себя так же в этом сценарии), а соседний, ранее не замеченный пробел - кандидат на отдельное код-уровневое решение, если проявится на практике.

**Также подтверждена реальная ошибка распознавания голоса в том же сообщении** ("Люху" вместо "Леху" в "Поздравить Леху и Бориса") - в этот раз не помешала (двусторонний substring-match зацепился за оставшуюся часть фразы), но это принципиальная точность STT-модели для имён/прозвищ, а не то, что можно исправить кодом на своей стороне.

## Батч фиксов по итогам полного аудита проекта (2026-07-28)

По запросу «проверь весь код и всю систему» три параллельных агента прошли CRM/Knowledge/намаз/колесо баланса/привычки/планировщик/напоминания, схему БД+миграции+Focus+Memory, интеграции Google/Gmail+HTTP API+безопасность; сам прошёл оркестратор/планировщик/задачи/голосовые. Итог: критичных межпользовательских утечек данных не найдено, схема и миграции без дрейфа. Найдено и исправлено в этом батче (гонка при сохранении памяти — отдельная, уже вынесена в фоновую задачу параллельной сессией, не входит сюда):

- **Нет перехвата исключений на верхнем уровне** — добавлен try/except в `dispatch_tool_call` (`tools_registry.py`, откатывает сессию при сбое инструмента, возвращает модели честный текст об ошибке вместо падения) и вокруг `handle_message` в `bot.py`/`api/routes/agent.py` (плюс отдельно вокруг распознавания голоса) - раньше любое необработанное исключение = полное молчание бота без единого следа для пользователя.
- **Напоминания: нечёткое совпадение слов вместо подстроки** — `find_recurring_reminders` (`app/core/reminders/service.py`) теперь сравнивает по целым словам (`{"звонить"} <= {"позвонить","маме"}` = False), а не по вхождению подстроки - раньше «звонить» матчилось с «Позвонить маме» и тихо отменяло чужое напоминание.
- **Намаз: enable теперь валидирует город ДО записи состояния** (`app/core/namaz/service.py`) - при реальной ошибке Aladhan (не любая опечатка, у Aladhan своя геокодировка и не все опечатки распознаются как ошибка - это отдельное, непофикшенное ограничение самого API) ничего не сохраняется вместо полу-включённого состояния. `disable` теперь сбрасывает `namaz_city`/`namaz_country` - раньше "включённость" оставалась навсегда после отключения.
- **Проактивные джобы игнорировали статус подписки** - `_run_job` (`app/scheduler/runner.py`) теперь пропускает (не деактивирует - чтобы само возобновилось при оплате) выполнение для пользователя с истёкшим триалом.
- **Просроченный Google-токен** (`app/core/integrations/service.py`) - `invalid_grant` теперь распознаётся отдельно от временного сбоя сети, битая запись credential удаляется, поднимается уже существующий `NotConnectedError` - все вызывающие места автоматически получают правильное "подключите заново" вместо бесконечного "попробуйте позже".
- **Даты не в часовом поясе пользователя** в колесе баланса и карточке контакта (`life_balance/service.py`, `_handle_get_contact_info`) - та же категория, что уже чинили для списка задач.
- **`create_contact` не искал существующий контакт** (`app/core/crm/service.py`) - теперь переиспользует по имени без учёта регистра, как уже делал `log_interaction`.
- **Отсутствие ffmpeg/ffprobe** в `speech_to_text.py` теперь оборачивается в `SpeechToTextError`, а не падает `OSError` мимо единственного except в `bot.py`.
- **`SECRET_KEY="change-me"`** - добавлен pydantic-валидатор, отклоняющий этот конкретный placeholder при старте (fail closed) - **реально сработал** на локальном dev-окружении, там до сих пор стоял этот placeholder несмотря на то что прод давно использует нормальный ключ; сгенерирован новый секрет для локальной разработки.
